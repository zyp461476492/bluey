# 07 决策记录（ADR）

**规则**：任何"我们决定用 X / 不用 Y"的技术选择都记在这里。
三个月后一定会有人（很可能是未来的你）问"为什么不用 React"，本文就是答案。
**只追加，不删除**；决策被推翻时新增一条并把旧的标为 `Superseded by ADR-xxx`。

格式：`## ADR-NNN 标题` + 状态 + 背景 + 决策 + 代价 + 推翻条件

## ADR-001 采用零构建的纯原生前端

**状态**：Accepted（2026-11-09）· **适用范围已于 2026-11-09 收窄至 `app/`**（见 ADR-009）

**背景**：项目由一个人 + AI 维护，使用场景是家庭客厅/平板/手机。功能复杂度极低
（单页、5 个状态、一个题库）。引入 webpack/vite 会带来 node_modules、锁文件、
构建缓存、"改了但没生效"的排查成本。

**决策**：只用浏览器原生能力：原生 ES Modules、原生 CSS 自定义属性、`fetch` 读 JSON。
不引入任何构建步骤、包管理器、编译型语言。

**代价**
- 无法用 TS 类型检查 → 用 JSDoc 注释补偿
- 无 tree-shaking / 代码分割 → 靠按分类懒加载 JSON 弥补，JS 总量本就小
- 无法用 npm 生态 → 需要的功能自己写（本项目也确实用不上）
- 直接双击 `index.html` 打不开（`fetch` 受 `file://` CORS 限制）→ 必须起本地服务，文档已说明

**推翻条件**：如果出现以下任一，(重新评估)
- 代码量超过 5000 行且模块耦合明显
- 需要接入 npm 生态的关键能力（如复杂动画库、PDF 导出）
- 需要打包成 TV 原生 App 安装包

## ADR-002 不使用 UI 框架

**状态**：Accepted（2026-11-09）· **适用范围已于 2026-11-09 收窄至 `app/`**（见 ADR-009）

**背景**：应用本质是"一张卡片 + 一个进度环 + 4 个按钮"。状态只有一个 store。
React/Vue 带来的响应式能力在这里收益极低，而运行时体积、TV 浏览器兼容风险、
虚拟 DOM 与遥控器焦点的配合复杂度都是实打实的成本。

**决策**：手写渲染函数。视图按"组件文件 + `render(state)` → 更新 DOM"组织，
store 变更时由顶层 `ui/app.js` 统一调度。

**代价**：需要自己处理局部更新与重渲染范围，容易写出全量 `innerHTML` 替换导致焦点丢失。
→ 缓解：焦点管理集中在 `ui/focus.js`，每次重渲染后显式恢复焦点（见 `03-ux-devices.md` §3.3）。

**推翻条件**：视图数量 > 10 个且存在大量交叉状态更新。

## ADR-003 题库用「一分类一 JSON 文件」

**状态**：Accepted（2026-11-09）

**背景**：题目数据要能被非程序员（家长）修改。可选方案：
(a) 单个大 JSON；(b) 一分类一文件；(c) 直接写进 JS；(d) 用 SQLite/IndexedDB。

**决策**：选 (b)。`data/questions/index.json` 做分类注册表，各分类独立文件。

**代价**
- 需要维护注册表，加分类要动两个文件
- 跨分类"全部"模式要并发 fetch 多个文件

**为什么不选其他**
- (a) 单文件：一处语法错误导致全站挂掉；文件会膨胀到难以 diff
- (c) 写进 JS：违反"题库是数据不是代码"，且不利于将来做家长编辑界面
- (d) IndexedDB：过度设计，静态 JSON 完全够用，且不利于用 git 管理内容版本

**推翻条件**：词条数 > 2000，或需要运行时写入（家长自建题库）→ 那时引入 IndexedDB 做缓存层，JSON 仍为源。

## ADR-004 答案揭晓用「5 秒固定倒计时」

**状态**：Accepted（2026-11-09）

**背景**：核心交互是"看图 → 思考 → 揭晓"。时长过短剥夺思考，过长孩子失去耐心。

**决策**：默认 5s，从**图片加载完成后**开始计时，倒计时可见且可跳过，用户可在 2–10s 区间调整。

**代价**：不同孩子节奏差异大 → 靠可配置 + 可跳过缓解，不做自适应（数据量不足以做个性化）。

**推翻条件**：有实际使用数据表明 5s 明显不合适（比如孩子普遍在 2s 内就喊出答案且表现出无聊）。

## ADR-005 发音用浏览器 TTS，不用预录音频

**状态**：Accepted（2026-11-09）

**背景**：150 个词条 × 2 语言 = 300 条音频。预录需要找配音、切音频、管资源，成本高；
浏览器 `speechSynthesis` 免费且零素材。

**决策**：用 `speechSynthesis`，语言 `zh-CN` / `en-US`。不可用时**静默降级**，不阻塞流程。

**代价**
- 音质取决于设备语音包，电视上可能机械或无声
- 语速/音色不可控（部分浏览器支持 `rate`，TV 上不一定生效）

**推翻条件**：用户反馈发音质量影响学习效果 → 为高频词条补 `audio.custom` 预录音频作为优先源（schema 已预留）。

## ADR-006 不做用户系统与云端

**状态**：Accepted（2026-11-09）

**背景**：加了账号就必然有注册流程、隐私政策（儿童产品尤其敏感）、后端运维。
而项目目标只是"家里能用"。

**决策**：进度与设置存 `localStorage`。不做账号、不做同步、不做家长后台。

**代价**：换设备/清缓存丢进度 → 可接受，进度本身是弱数据。

**推翻条件**：真的需要多设备同步 → 那时再评估后端，且必须重新过儿童隐私合规。

## ADR-007 应用名 Bluey 与仓库同名的说明

**状态**：Accepted（2026-11-09）

**背景**：仓库名为 `Bluey`（澳大利亚儿童动画片名，与"蓝色小狗"形象强关联）。

**决策**：仓库名沿用；应用对外展示名先用「Bluey 猜词」，**不使用任何 Bluey 动画的角色形象与素材**。
**使用范围确认为家庭内部使用，不涉及商业**（2026-11-09 用户确认）。

**代价 / 边界**
- 家庭自用 → 名称与素材的商标/著作权风险极低，ARASAAC 等 NC 素材也可以使用
- 但"家庭内部"的边界在**对外传播**（发链接、发群、发社交平台）那一刻就被突破，
  届时须按 `docs/09-asset-pipeline.md` §2.4 把 `仅家用` 素材全部替换，并重新评估名称

**推翻条件**：决定公开发布或商业化 → 必须改名 + 清理 NC 素材 + 重做视觉，成本约等于重做素材。

## ADR-008 素材路线：先开源 Emoji，再 AI 精修核心词

**状态**：Accepted（2026-11-09）· **优先级已由 ADR-011 反转**（用户决定 AI 为主、OpenMoji 为辅）

> ⚠️ **修订说明**：本文原本建议"M1–M2 用 emoji 起步，M3 后再做 AI"。
> 用户在看过 12 张打样后（`docs/09-asset-pipeline.md` §8）决定**反过来**：
> AI 手绘为主，OpenMoji 只在额度不足或人工指定时兜底。
> **本文关于素材来源与规格的部分仍然有效；关于"先 emoji 后 AI"的顺序已作废，以 ADR-011 为准。**

**背景**：150 个词条需要图片。三条路：开源图库、AI 生图、买商用套装。
AI 生图能做出"手绘钝感风"，但一致性靠工程纪律维持、废片率 30–50%、
全库 150 词约需 1100–2200 额度 + 6–9 小时人工筛选。

**决策（建议）**：分阶段
1. M1–M2 用 **Noto Emoji（Apache 2.0）/ Fluent Emoji（MIT）** 的 SVG，
   全库统一、可任意改色、免署名、2 小时可完成 150 词
2. M3 之后，对"核心 50 词"用 AI 生图重做，走风格锚 + 固定提示词模板
3. 抽象概念词（情绪/动作/方位）可用 **ARASAAC（CC BY-NC-SA，仅家用）** 补位
4. **同一分类内不混视觉来源**；跨分类可以各用各的（孩子一次只玩一个分类）

**代价**
- 早期视觉不像"手绘"，但一致性满分
- 后期换图要重跑一次素材流水线

**为什么不一开始就 AI 生图**：产品还没被孩子验证"会不会玩第二遍"，
此时投入 6–9 小时做素材，是拿最贵的资源去优化最不确定的部分。

**推翻条件**：如果打样 A/B 显示 AI 手绘版可识别度显著优于 emoji，
且你确认要做"手绘风"这一件事本身（而不只是为了好看），则直接转全库 AI 路线。

## ADR-009 双制品分离：app 零构建，studio 用现代栈

**状态**：Accepted（2026-11-09）

**背景**：需求从"一个猜词小游戏"扩展出"题库与素材生成器"。生成器需要数据库、批量操作、
图片处理、后台表格 UI——这些都需要构建链和依赖。若与运行时应用放在同一个制品里，
会把 `node_modules`、构建产物、TV 浏览器无法消化的框架代码带进孩子的播放器。

**决策**：拆成两个独立制品，依赖方向单向：

```
studio/（生产端，可用 Node + Vue + Vite + SQLite）
   │  导出
   ▼
data/ + assets/（契约，唯一的接口）
   │  只读
   ▼
app/（运行端，纯静态、零构建、零依赖）
```

- `app/` 不知道 `studio/` 存在；删掉 `studio/`，`app/` 照常跑
- ADR-001（零构建）与 ADR-002（不用框架）**不废除，但适用范围收窄到 `app/`**
- 接口是 `docs/04-data-model.md` 里的 JSON schema，两边都不许绕过它直读对方内部结构

**代价**
- 需要维护两套依赖（但 studio 的依赖出问题不影响孩子用）
- 两个端口、两个启动命令（已约定：App 5173 / Studio 前端 5174 / API 5175）
- 数据要从 SQLite 导出成 JSON 才能给 App 用（这是刻意的单向边界，不是麻烦）

**为什么不合并**：合并后每次升级 studio 都可能让 app 跑不起来，
而 app 是给孩子用的——它挂掉的代价比"多一个导出步骤"高得多。

**推翻条件**：如果哪天用 Electron/Tauri 打包成桌面应用，两者可以重新合并；
但那是发布形态变化，不是架构演进。

## ADR-010 SQLite 做工作库，JSON 做发布产物

**状态**：Accepted（2026-11-09）

**背景**：素材管理需要状态机（生成/清洗/审核/发布/废弃）、额度账本、按分类查缺口、
生成尝试历史、图片指纹去重。这些用 JSON 存会很快退化成手写的残缺数据库。

**决策**：
- **`studio/data/studio.db`（SQLite）是可写的事实来源**，管词条、工单、素材、额度
- **`data/questions/*.json` 是只读的发布产物**，由 `publish` 命令单向导出

两条铁律：
1. Studio 从不读 `data/questions/`（那是输出，不是输入）
2. App 从不读 `studio.db`（它甚至不知道有这个文件）

**代价**
- 需要迁移脚本管理 schema 版本
- 发布是一次显式动作，不能"改完立刻生效"（但这正好是想要的安全边界）

**为什么不直接改 JSON**：见 `docs/10-studio-architecture.md` §4.1 的对照表——
状态机、聚合、并发写、去重索引，四项里 JSON 一项都撑不住。

**推翻条件**：词条数 < 30 且永远不做批量生成 / 额度统计 → 那确实不需要数据库。
但既然要做生成器，这个前提不成立。

## ADR-011 素材来源策略链：AI 主、OpenMoji 辅，降级必须可见

**状态**：Accepted（2026-11-09）

**背景**：用户确认"AI 手绘为主，OpenMoji 为辅助（额度不足或人工指定时）"。
这必然导致同一分类内出现两种视觉来源，与 ADR-008 里"同一分类内不混源"冲突。

**决策**：修正 ADR-008 的规则，而不是假装不冲突。

1. 来源按 `strategy: ["ai", "openmoji"]` 顺序解析；可被 `word.source_override` 强制覆盖
2. 降级产生的素材标记 `provisional = 1`，发布前必须显式确认
3. 系统必须随时能报出"哪些分类在混源、混了几张"（`v_mixed_source` 视图）
4. 单分类混源比例 > 30% → 提示"建议整类切换"
5. **核心分类**（数字、颜色、常用动物）配置为禁止混源，降级时跳过该词

**新原则**：**混源不是事故，无意识的混源才是。**

**代价**
- 发布前多一道混源确认
- 需要维护"核心分类"名单

**推翻条件**：额度充足到不需要降级 → 策略链退化为单一 `["ai"]`，其余机制自然失效但不碍事。

## ADR-012 Studio 技术栈：Node 22 + Express + node:sqlite + React 18 + shadcn/ui

**状态**：Accepted（2026-11-09）· 前端经用户改选为 C（React + shadcn/ui）

**背景**：本机已有 Node v22.22.2 / npm 10.9.7 / Python 3.13，无 pnpm，无 sqlite3 CLI。
Studio 是本地单机内部工具，重点是"少折腾、能快速出表格界面"。

**决策**

| 层 | 选择 | 关键理由 |
| --- | --- | --- |
| API | Express 5 | 最成熟，本地单机不需要更多 |
| 数据库驱动 | **`node:sqlite`**（Node 22 内置） | **零原生编译**，Windows 不用装 VS Build Tools |
| 前端框架 | **React 18 + Vite** | 生态最大 |
| 组件 | **shadcn/ui** | **源码进项目，可改到任意样子**；不是 npm 包 |
| 样式 | Tailwind CSS | shadcn/ui 的前提 |
| 表格 | TanStack Table v8 | shadcn 的 DataTable 方案 |
| 表单 | react-hook-form + zod | shadcn Form 默认搭配 |
| 数据请求 | TanStack Query | 缓存与失效重取，省掉手写 loading |
| 语言 | **TypeScript（strict）** | shadcn 组件本身就是 `.tsx`，不用 TS 反而别扭 |
| 图像处理 | sharp | 有预编译二进制，webp 质量好 |

**当初的三个候选**（保留记录便于复评）：

| 选项 | 栈 | 取舍 |
| --- | --- | --- |
| A | Vue 3 + Element Plus | 表格开箱即用，但视觉难改 |
| B | Vue 3 + Naive UI | 轻、现代，表格弱 |
| **C（选定）** | **React + shadcn/ui** | 可定制性最好，代价是表格要自己拼 |

**代价（必须接受的）**
- `el-table` 那种"传 columns 就出表"的便利没有了，表格要用 TanStack Table 手写列定义
- 缓解：`components/DataTable.tsx` 做**一次**通用封装，四个页面共用。
  不做这一步，后面会各写一遍
- `node:sqlite` 在 Node 22 会打印 ExperimentalWarning

**风险与缓解**：`node:sqlite` 若改 API，只需改 `server/db.ts` 一个文件。
**纪律：SQL 不许写在路由里。**

**推翻条件**：需要多人协作 / 部署到服务器 → 换 Postgres + 全栈框架。

## ADR-013 年龄档是"配置档"，不是"内容分库"

**状态**：Accepted（2026-11-09）

**背景**：题库要覆盖 2 岁到 8 岁。直觉做法是按年龄建三套题库，
但那样素材要生成三遍、内容维护三份，而核心差异其实只在**玩法参数**上。

**决策**：
1. 一套词库（`words`），每个词带 `min_age`
2. 三个年龄档（`toddler` 2–3 / `preschool` 4–5 / `school` 6–8）存为 `age_profiles` 配置
3. App 按当前档位过滤 `min_age <= 档位`，并用配置决定玩法

**关键判断**：**2 岁不做"猜"，做"认"。**
"猜"需要"我知道答案你不知道"的心理理论，3 岁后才成熟。
所以 toddler 档是**闪卡模式**（图 + 词 + 发音同时出现、自动翻页），没有倒计时悬念。

**代价**
- 一个词条要维护"在三档里分别怎么呈现"的心智模型（但代码上只是一份配置）
- 加新档位要重新过一遍内容规则（`11-curriculum-design.md` §6）

**推翻条件**：如果发现不同年龄档需要**完全不同的词表**（而非共享），
才考虑拆库——目前数据不支持这个结论。

## ADR-014 生成前必须预估额度，不足时改默认值而不是报错

**状态**：Accepted（2026-11-09）

**背景**：AI 生图按次计费，全库 116 词预估 685–1370 额度（`11-curriculum-design.md` §8）。
如果不预先告知，用户会在跑到一半时才发现额度没了，而那时已经生成了一半风格一致的图，
既不能整批降级（风格会裂），也不能停（半成品没用）。

**决策**：
1. **下单前必算预估**：`G = ceil(N ÷ usableRate)`，给出额度区间
2. `usableRate` **从自己的账本校准**（最近 3 批的 `1 − 废片率`），不写死
3. 预算达 80% 时，**新建工单的默认 source 自动切成 openmoji**，要用 AI 需手动确认
4. 预算达 100% 硬停 AI 工单，只能 openmoji / manual
5. 单批预估 > 150 额度 → 二次确认
6. 额度不足时**永远给三个选项**（减少数量 / 整批降级 / 拆批），不给一个"额度不足"的报错

**为什么第 3 条是关键**：人在预算快用完时容易"就再来一批"。
把默认值换成免费方案，比弹提醒有效——**改默认值胜过硬约束**。

**代价**
- 多一层预估逻辑与一次校准视图（`v_waste_rate`）
- 预估必然不准（首版按 85% 可用率保守估），要接受区间而非单值

**推翻条件**：额度无限（或改用本地模型）→ 预估降级为只做统计，不拦截。
